# 音频算法可视化平台测试与验收准则

## 1. 使用方法与通过语义

本文与 [开发方案](plan_audio_pipeline_editor_juce.md)、[Agent 迭代规程](agent_loop_audio_pipeline_editor.md)共同使用。所有测试 ID 是待实现的验收要求，不代表已有测试或通过结果。实现测试应标注对应 ID，测试注册清单包含 Gate、必需性、执行器和子用例。

2026-10-18：算法库与编辑器分离另按[重构测试及通过准则](testing_architecture_refactor.md)验收AR-01～20的全部字母子用例；实施与方法见[重构方案](plan_architecture_refactor.md)、[重构Agent规程](agent_loop_architecture_refactor.md)。AR结果补充本文，不能替代G0～G6或NED；主验证器漏收QUAL章节/skip/桌面证据等问题须按AR-02真实修复，不能把当前脚本退出0视作全部验收完成。

每个 ID 可以包含多条实际用例；该 ID 只有全部必需子用例通过才算通过。`passed`、`failed`、`not_run`、`not_verified`、`blocked`、`skipped` 分开记录；后五者均不能使对应必需 Gate 通过。阶段必需集合为开发方案 Gate 表中的集合，加全部前序 Gate 集合，G6 为全文全部 ID。

算法数值正确性、算法质量、运行性能、GUI 行为分别判定，不能互相替代。用 mock 测取消和旧结果合法，但算法 Gate 必须使用真实实现。纯组件测试不能替代真实桌面交互；无设备环境不能报告播放已验证。

只有可选的平台/设备扩展可跳过；目标 Windows、首版算法、Python、GUI 交互和真实播放的测试不可在最终验收中跳过。真实阵列数据缺失时允许继续开发其他功能，但 QUAL-03 和 G4/G6 保持未完成。

## 2. 测试基础设施与环境

- C++ 使用 Catch2 + CTest；Python 使用 pytest。每个测试有独立临时工作目录，不共享可变算法实例或全局文件名。
- headless 集合不创建窗口、依赖声卡或访问互联网；GUI 集合单独标记，需要 JUCE 消息环境和可用桌面会话。
- 使用固定随机种子、采样率、通道、分帧、精度、初始状态。OpenMP/BLAS 等线程设置记录到报告；必要时固定为单线程以减少非确定性。
- 单元默认超时 10 秒，原生集成 60 秒，Python/算法质量 180 秒；慢测试单独标记。取消/恢复用更严格的专用预算。
- CTest 必须使用 `--no-tests=error`；执行前通过 CTest JSON inventory/pytest collect 检查预期测试存在；测试进程零退出也不能掩盖收集数量为零。
- G0 的故意失败探针验证“断言失败 → 测试非零 → Gate 非零”的链路；验证完成即移除故意失败用例，保留其日志，不能留成永久失败测试。
- 不要求为简单样式、颜色和文件名实现镜像测试。测试应验证输入输出、边界、状态、时序和可观察行为。

### 2.1 固定开发数据

| 数据 ID | 内容 | 独立性与用途 |

| F02 | 双/四通道，各通道独立频率或单样本脉冲 | 证明通道顺序、分支与端口映射；内容必须可区分 |
| F03 | 固定 seed 噪声、随机 host 块划分、串联帧长 480/512 | 检验固定帧适配和跨块状态 |
| F04 | 自有/明确授权干净语音 + 固定 seed 稳态噪声，输入 SNR 0 dB、10 dB | 降噪质量；至少三条语音，每条 10 秒以上；保留 clean/noise/mixture |
| F05 | 独立生成的 render，经固定因果 FIR 和已知延迟得到 echo；另有独立 near-end | AEC；远端单讲、近端单讲、双讲、路径切换分别生成 |
| F06 | 四麦克风远场平面波，由解析时间延迟生成；目标与干扰可单独导出 | 不调用被测波束形成库生成 oracle；方向/几何/抑制验证 |
| F07 | 授权清晰的真实同步四通道阵列录音，已知几何与目标/干扰方向 | 真实波束验收，含目标单独、干扰单独、混合录音及通道说明 |
| F08 | 60 秒四通道与 10 分钟四通道 float 音频，48 kHz | 长文件、GUI 缓存及资源测量；可由解析信号生成 |

文件由版本化脚本一次生成，保存 manifest、seed、算法参数、许可及 SHA-256；测试不在每个分支重新随机合成。大音频不直接提交到源码树；保留生成配方或下载来源/哈希。预期 hash 若依赖平台需声明适用平台；数值验收以解析 oracle 与固定容差为主。

### 2.2 默认数值规则

| 场景 | 通过准则 |
|---|---|
| float32 Gain/直通/通道重排 | 对独立 float64 oracle，逐样本满足 `abs(actual-expected) <= 2e-6 + 1e-5*abs(expected)`，长度、通道、起点必须精确一致 |
| PCM16 往返 | 未削波输入误差不超过 1 LSB；超幅输入饱和，无整数回绕；裁剪计数精确 |
| 同平台 Speex 直调/adapter/runtime | 经过相同量化/分帧后 PCM16 差异不超过 1 LSB，float 转换后绝对差不超过 `1/32768 + 1e-6`；无额外丢样、移位或 reset |
| Python/C++ Gain | 使用 Gain 默认容差，固定相同参数、布局与有效区间 |
| Python 库直调/Node | 同环境、精度、seed 与分帧，对相同形状结果 `atol=1e-5, rtol=1e-4`；额外库非确定性必须先解释和单独定义，不现场放宽 |
| 声谱幅值 | 对解析正弦主峰频率误差不超过一个 FFT bin；远离零值的幅值与独立参考相差不超过 0.5 dB；窗口/归一化相同 |
| 时间与样本 | 恒等/无延迟节点首样本和总样本数精确一致；适配延迟按声明精确到样本，必须区分原始和逻辑对齐产物 |

上述是项目首版验收阈值，不是第三方库的效果承诺。出现不满足时先诊断代码、数据和适配；真实证据证明契约不适用时须在修复前写决策记录、给出独立依据并同步文档，禁止按当前输出反推阈值。无法满足仍保持失败。

### 6.2 降噪质量 QUAL-01（G4）

F04 的三条以上语音分别运行 0/10 dB 输入 SNR。干净信号的活动区间由数据生成 manifest 固定，不根据被测输出选择；首 0.5 秒预热排除但保留报告。

- 0 dB 稳态噪声场景：按固定对齐、无额外响度归一化的 clean-reference SNR，中位提升 ≥2 dB。
- 所有场景：SI-SDR 中位变化 ≥0 dB，单条退化不得低于 -1 dB；静音、NaN 和全零退化输出直接失败。
- 干净语音单独通过处理器：活动区间 RMS 增益在 -3～+3 dB，排除“把声音全部压掉”的伪改善。
- 全零输入输出 peak ≤1e-5，无 NaN/Inf。
- 至少记录一轮真实听评的音频清单和发现；听评不能替代上面的数值断言。

固定指标公式、延迟补偿、活动区间和分帧。若当前 Speex 参数无法满足，该场景保持失败，检查预处理配置、幅值和算法适用性，不把当前输出自动批准成 golden。

### 6.3 AEC 质量 QUAL-02（G4）

F05 使用 16 kHz、20 秒受控输入；render 为持续激励的宽带信号，已知固定延迟与 128 ms 以内 FIR 声学路径；不让测试难度超过该配置的滤波长度。保留 echo/near-end 独立参考。前 5 秒适应，固定第 5～15 秒为静态路径评估区间。

- 远端单讲：`ERLE=10*log10(sum(echo^2)/sum(residual^2))` ≥10 dB，静音/近零分母用预定义 epsilon，不能挑选最好片段。
- 近端单讲：处理后活动语音 RMS 增益在 -3～+3 dB。
- 双讲：相对于 clean near-end 的 SI-SDR 与未处理 capture 相比变化 ≥-1 dB；报告 near-end 保真与残余回声，不能用整体 ERLE 评价双讲。
- 路径切换：第 10 秒切换到另一固定 FIR，第 15～20 秒远端单讲 ERLE ≥6 dB，单独记录恢复曲线。
- 输出长度、有效区间和 delay 与报告一致，无 NaN/Inf、状态串用或静默丢参考。

这些门槛针对受控接入及基础效果验收，不代表真实设备全场景 AEC 合格。真实设备 AEC 与漂移补偿另立后续 Gate。

### 6.4 波束质量 QUAL-03（G4）

解析 F06：48 kHz，四个麦克风位于 `((i-1.5)*0.035,0,0)` 米，声速 343 m/s。目标 broadside 单位方向 `(0,1,0)`、1 kHz；干扰方向 `(sin60°,cos60°,0)`、4 kHz。使用独立解析相位延迟合成，跳过固定首尾瞬态区间；输出评测采用与库一致且预先记录的方向约定。

- 目标方向 DAS 的 1 kHz 增益在 -1～+1 dB，输入/输出按相同物理幅值比较。
- 相对任一参考麦克风，4 kHz 干扰的输出 SIR 提升 ≥6 dB；分量能量通过固定频率投影测量，不使用被测库的指标实现。
- 同时重排通道及对应几何，结果与原排列在默认浮点容差内等价；只重排音频导致的错误可被数据契约诊断或方向回归用例捕获。
- 目标方向从 broadside 改到另一预设方向时，所需输出随之变化；用独立期望响应验证，不只断言“两个文件 hash 不同”。
- F07 真实录音：已知目标/干扰分别录制的有效区间，相对预先选定参考麦克风，目标转向后 SIR 提升 ≥3 dB，目标单独录音 RMS 增益在 -3～+3 dB；方向、阵列、房间和采集条件入报告。

F07 若无法获得可靠分量参考，记录为探索性听评数据，不能用它替代上述真实质量准则；继续获取合格数据。仿真测试全过只能声明仿真正确，不能把 QUAL-03 标为全部通过。

## 9. Gate 自动化与证据格式

`scripts/verify_gate.py` 读取版本化测试映射清单，定位构建 preset，执行对应集合，并比对 inventory。必须保留实际子进程命令、退出码和完整原始日志；通过日志路径/内容哈希关联报告。不可只生成一份 pass 字符串。

机器报告建议结构如下（仅示例，全部真实结果应由执行器生成）：

```json
{
  "schema_version": 1,
  "gate": "G1",
  "status": "not_run",
  "source_revision": null,
  "source_tree_hash": null,
  "environment_manifest": "environment.json",
  "checks": [{
    "requirement_id": "DSP-01",
    "test_name": "gain_matches_independent_oracle",
    "status": "not_run",
    "command": [],
    "exit_code": null,
    "log_path": null,
    "duration_ms": null
  }],
  "missing_required_ids": ["DSP-01"],
  "artifacts": [],
  "limitations": ["示例结构，未执行测试"]
}
```

没有 Git 仓库/commit 时使用源码清单内容 hash，不能自动初始化/提交 Git 伪造 revision。测试证据与当前源码变更关联：实现修改后只允许复用未受影响的旧检查，关联与理由明确；打包前必须执行一次当前最终源码的完整 Release 累计回归。

GUI 证据至少含操作步骤、操作方式、环境、时间、屏幕/录屏、项目/run ID 和实际观察。截图只能证明显示状态，数值结果仍需读取本次产物独立核对。不得使用图像生成或静态假界面制作验收截图。

## 10. 失败处理与结束条件

失败按构建/环境、契约/实现、第三方适配、数据/指标、GUI/设备分类；先重现再定位最小层。任何已知阻断缺陷、必需测试失败或缺失均阻止对应 Gate 完成。

不能把实际失败改成预期失败来通关，也不能把 unavailable 当作可选跳过。无许可数据、无真实设备或工具权限不足要说明具体缺口，同时推进其他不依赖该条件的开发。最终交付必须如实区分已实现、已验证、未验证和后续范围。
