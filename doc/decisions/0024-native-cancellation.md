# 原生协作取消与发布边界

2026-10-22。真实Red在`P2-cancel/actual-behavior-red.json`：取消在首个处理块内发出，旧实现仍执行5块，保留目录并发布complete。首轮`behavior-red.json`的30秒超时来自测试把JUCE消息线程阻塞在worker.join，属测试设置失败；修正为消息线程准备图、独立控制线程在真实处理块内请求取消后，得到上述语义Red。

RunRequest增加单调、非阻塞、不抛异常的worker侧取消谓词。RunService在准备前、资源快照/哈希块、原生处理块前后、产物/成功标记发布前检查；原生区域返回run_cancelled，OutputDirectoryGuard清理本次保留的新目录，既有成功产物不改写。请求/完成身份仍由既有RunIdentity及接收入口控制。

complete.json前的最后检查是协作取消/终态提交边界，之后发布标记即成功终态；不能承诺中断正在执行的第三方函数、整次文件系统调用或该最终提交。EditorRunJob将JUCE任务退出标志转发至同一路径，不强杀原生线程。关闭任务池仍先请求停止、等待回收、最后释放注册表/模块。

定向验收包含：首块取消后只执行1块、末块取消无complete、预取消零处理器执行、目录清理、≤5秒受控恢复、随后实际Gain成功且旧成功hash不变。每项目一个执行+一个最新待执行的有界队列、New/Open主动取消及50次/心跳验收是接续范围，不能由该谓词接口声称已完成。

直接回归`direct-regression.json`中AR-09.d旧RunJob用例在关闭视图后立即调用shutdown_async(true)，却仍要求这条已收到退出信号的任务发布完整音频。旧后端无取消能力时该断言成立；现在它与重构方案§7“关闭应用先停止接收、取消、回收任务，再销毁registry/backend”、AR-17.c及AR-16.d冲突。更新验收依据为：独立观察到ThreadPool退出信号、真实处理器只完成首块、关闭分支目录/成功标记/音频均不存在、无悬空回调且模块回收；活跃视图分支仍成功并保留全部原数值oracle。原失败日志不改写，不降低数值/时间阈值，不改活跃分支输出期望。
