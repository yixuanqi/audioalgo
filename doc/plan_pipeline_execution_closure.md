## 2. 产品出口

用户不需要关心节点语言背后的运行方式。共同流程为：

```text
新建/编辑源码与定义
    → 后台检查/构建及契约试跑
    → Apply完整不可变版本
    → Node Library出现节点
    → 拖入Canvas并连接有类型端口
    → Run整条Pipeline
    → 查看实际结果、每个节点的日志及错误
```

Python检查通过后Apply可即时刷新库。C++编译及独立probe通过后，先显示PendingRestart，用户正常保存并重启后激活；不承诺当前首版热加载/热卸载。保存草稿、检查候选、应用版本、升级工程是不同操作，失败不能覆盖旧可用版本。

第一条纵向例子使用当前PCM入口约定：

```python
def process(inputs, params, state):
    print("aaaaaaa", flush=True)
    return {"audio_out": inputs["audio_in"]}
```

节点名为Print。Apply后库中出现Print，拖入`File → Print → Output`，Run后日志可见`aaaaaaa`且输出音频与输入一致。process按音频块调用，出现多行属正常行为；测试明确预期次数，不把恰好打印一次作为通用约定。检查试跑也可能打印，必须与正式Run分开展示。

此例只是第一条可观察用例。完整出口必须再执行`File → C++ A → Python B → C++ C → Output`与Python→C++→Python，不以单个print、能import、生成DLL或仅出现库条目代替运行成功。当前范围是声明支持的PCM链；任意独立脚本、无端口任务、任意数据类型或低延迟实时混合不隐式取得支持。

## 3. 根路径修复

1. 路径处理区分**逻辑绝对路径**与**Win32 I/O路径**。父目录、文件名及根目录语义尽量在普通绝对路径上计算；扩展前缀只在实际系统调用边界生成。输入已带扩展前缀时先按明确规则规范化，保留UNC共享根和卷根语义。
2. 消除Draft.cpp中“先加扩展前缀，再直接parent_path”的依赖；检查用户文件、恢复副本、绑定侧文件和目录探针四个消费者。只修受影响调用，不扩成全仓路径重构。
3. 不能通过去掉长路径支持、拒绝根目录、改选子目录或修改ACL使测试通过。保留重解析点/链接拒绝、大小限制、冲突检测、同目录临时文件及原子提交。
4. 创建目录失败明确记录操作、实际目标、系统错误码；区分路径非法、存储拒绝、低完整性及文件外部修改。显示“保存失败，内容保留”，不附虚假源码0:0。
5. 保留正常运行副本部署及低完整性检查；它处理的是独立的权限问题，不能替代此次路径缺陷修复。

## 4. 混合执行继续沿用共同运行服务

```text
Canvas工程/精确版本锁/参数快照
    → RunService：预检、冻结资源和代码、生成执行计划
    → C++原生区域 ↔ 有所有权的数据边界 ↔ Python独立任务
    → 校验并发布本次输出和运行报告
    → UI按运行身份接收状态、日志和结果
```

运行准入由端口、格式及执行能力驱动，不在Canvas添加按算法名、print文本或语言内容猜测的分支。保持project模型唯一权威；JUCE图及混合计划是执行投影。

每条边核对端口ID、类型、采样率、通道ID/顺序、帧数及有效区间。dtype/shape/NaN/Inf等违规明确定位node/port；不同长度、延迟、尾部只执行已有明确支持的契约，不静默补零/裁剪/改类型。已有共享上游一次执行、固定帧FIFO、已知延迟裁剪和EOS语义必须回归，不能重写成简单逐节点整段调用后丢掉这些能力。

每次Run持有完整工程、catalog、代码版本和参数快照；Apply新版本不改变运行中任务或已锁旧版本的工程。GUI与CLI继续使用同一解析/运行服务。统一用户操作不要求所有节点在同一进程执行，也不意味着低延迟实时能力已完成。

## 5. 统一日志、进度及诊断

### 5.1 共同事件与展示

新增最小共同事件/报告职责，正式类型名在实施时检查后确定，不把下列名称当现有API。事件至少携带：

- 检查/构建：draft_id、generation、源码/声明hash、request_id、阶段。
- 正式运行：project_id、session_epoch、request_id/run_id、revision、node_id、type_id、准确版本/hash。
- 内容：节点内单调序号、时间、级别、来源stdout/stderr/SDK、消息、截断或丢弃计数。

跨节点事件按实际接收顺序显示，不能声称具有无法保证的全局打印先后。日志与音频端口数据分离，不把print字符串伪装成音频输出。

编辑器底部提供“波形 / 运行日志”入口；工作台提供“检查/构建日志”。支持复制、按节点及级别查看、查看本次报告位置。打印文本按纯文本显示。既有波形、状态栏、画布及Inspector功能保留。

Worker采集并批量投递值对象；UI不得读取完整运行目录、同步等待进程或在每条日志上重建整个文本区。沿用EditorRunJob、completion dispatch与apply_if_current_run身份门禁，覆盖进度和中间日志，而非只保护最终结果。切换工程、修改revision、新Run或关闭面板后，旧日志不得污染当前视图；旧运行记录可独立查看。

终态与日志独立携带。成功、异常、取消、超时均能留下本次诊断/受限日志；不能只在成功RunSuccess时读取provenance。失败不发布本次成功产物，不覆盖旧运行文件，不把上次成功摘要当成本次结果。当前结果过期/播放资格仍遵守既有合同。

### 5.2 Python

复用PythonTask已有独立进程stdout/stderr管道。第一片先将已有成功日志接到生产UI并让Print用例Green；随后补检查、失败及运行中事件，均用同一归属模型。无需更改控制协议去通过stdout传消息，stdout永远是用户日志。

当前每流64KiB尾部不自动放宽。补齐既有方案中每任务完整日志≤16MiB、UI合计尾部≤256KiB及超限log_limit/回收要求；文件保存到任务所属目录，失败清理载荷时保留可定位的有界诊断。原始字节总数、尾部丢弃及完整日志超限分别报告。超限停止/回收自身任务，不让reader线程静默吞掉无限输出。UTF-8跨chunk、多线程输出和stderr分开验证。

### 5.3 C++

进程内DLL不能依靠全局重定向cout/printf实现可靠节点归属；这会混入宿主和并行节点输出。C++模板使用明确的SDK日志接口，宿主统一转为上述事件。不能要求旧ABI v1 process回调直接写控制台/文件，或为了日志放宽其禁止I/O约束。

发布SDK的`node_abi_v1.h`保持字节/布局和原入口契约。日志能力通过新版本入口或明确版本协商的可选扩展提供；新宿主兼容旧v1，缺日志扩展的旧DLL仍能计算，并明确说明未提供用户日志。不能向旧结构体无条件追加字段或跨DLL传std::string/异常。

处理回调只写入预分配、有界、非阻塞的事件队列，不分配、不锁等待、不访问UI或文件；worker侧批量消费、落盘和展示。队满有明确丢弃计数/诊断，不无限增长。实例持有的日志目标和模块租约在worker/队列回收后释放。新增SDK扩展须真实运行旧v1二进制及新SDK仓库外消费者。

当前正式C++执行仍在宿主进程。独立probe可隔离构建候选的崩溃/挂起，但不能承诺任意C++运行崩溃后宿主必定存活；如需该保证，另做原生独立runner能力及协议验收，本补充方案不暗中改成全隔离运行。

## 6. 应用内C++构建与激活

复用现有编辑面板、不可变包、版本锁、后台队列及发布SDK。用户编辑算法函数与定义，生成薄包装和独立CMake工程；不将生成算法源码加入宿主构建。源码诊断映射回用户代码。

流程：冻结源码/SDK与工具身份 → 仅用SDK独立编译DLL → 新进程校验导出/ABI/描述并做数值及生命周期probe → 原子安装候选及索引 → PendingRestart → 用户正常保存重启后激活 → 库中拖入并Run。发布包记录平台/架构、SDK/ABI、源码/声明/二进制hash与依赖。

缺编译器、编译失败、缺依赖、ABI错或probe失败均保留草稿和旧默认版本，不能将待检DLL先载入宿主。构建/probe只回收自身Job Object；不自动安装工具链或联网。部署新节点前后已安装宿主EXE hash应保持一致；新增日志ABI的宿主升级属于平台本身一次性修改，不能与此独立节点准则混淆。

首版原生v1仍仅支持其声明的full-block PCM能力；内部固定帧流式接口不能被误当成已发布ABI能力。新增不支持的能力要前置拒绝并明确解释。
